# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Hebrew (RTL) school-year timeline ("ציר שנת הלימודים") for תשפ"ז (Sept 2026 – Aug 2027), now a Node app:

- `server/` — Express API + file-based JSON persistence + a cron scheduler hook.
- `client/` — React (Vite) frontend: a public viewer page and a password-protected `/admin` page for editing the data.
- `timeline.html` — the original static single-file version. It is **frozen**, kept only as a visual/structural reference (the client's CSS and component structure were ported from it 1:1). It is not served by the app and is not updated when the data changes.

## Commands

From the repo root:
- `npm install` then `npm run install:client` — install server and client dependencies (first time only).
- `npm run dev` — runs the Express API (nodemon, port 4000) and the Vite dev server together; Vite proxies `/api/*` to Express (see `client/vite.config.js`). Open the Vite URL it prints. `nodemon.json` deliberately excludes `server/data/` from its watch list — theme switches still write `themes.json` there, and without that exclusion nodemon restarts (and silently drops the in-memory `express-session` store, logging out `/admin`) on every single edit. Event mutations no longer touch `server/data/` at all (see **Persistence: a pluggable layer, Firestore + Cloudinary** below), so this exclusion matters less than it used to, but is harmless to keep.
- `npm run build` — builds the client into `client/dist`.
- `npm start` — runs `node server/index.js` only; if `client/dist` exists, Express serves it directly, so this is the single-process production mode (one port for UI + API).
- `npm run emulator:firestore` — runs a local Firestore emulator (no real project/credentials needed) for local dev against `FIRESTORE_EMULATOR_HOST=localhost:8080` instead of a real Firebase project.

Config is via env vars (see `.env.example`, loaded through `dotenv`): `PORT`, `ADMIN_PASSWORD` (shared password gating all `/admin` mutations), `SESSION_SECRET`, `SCHEDULER_CRON`, `DATA_DIR` (still used by `themeStore.js`; also what tests use to redirect that persistence to a temp dir instead of the real `server/data/`), `DB_PROVIDER` (which persistence adapter to use - see **Persistence** below; defaults to `firestore`), `FIREBASE_SERVICE_ACCOUNT_JSON`/`FIREBASE_PROJECT_ID` (Firestore credentials - events + their history - see **Data model** below), `ACTIVE_SCHOOL`/`ACTIVE_CLASS`/`ACTIVE_PERIOD` (which dataset this server instance reads/writes), `CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET` (event images; falls back to inline data URIs if unset - see **Data model**), and `BACKUP_CRON`/`BACKUP_MIN_INTERVAL_DAYS`/`CRON_SECRET` (full-dataset backups - see **Backups** below).

### Tests

**Rule: every new implementation (new endpoint, new `timelineStore`/service function, new business rule or validation, new non-trivial UI behavior) must come with tests covering the new business requirement(s), and the full suite (`npm test`) must pass alongside them before the work is considered done.** This isn't optional polish — a feature without a test is treated as incomplete, not as a follow-up. Match the existing per-area test shape rather than inventing a new one: `server/services/__tests__/*.test.js` for store/service logic (validation rules, computed results), `server/__tests__/*.integration.test.js` for routes (via `createTestApp()` + `supertest`), `client/src/**/__tests__/*.test.jsx` for component behavior worth asserting on. If a change doesn't fit any existing test file, add a new one next to the code it covers rather than skipping coverage.

- `npm test` — Vitest: unit + component + integration, fast, no browser. Single run per invocation (`npm run test:watch` for watch mode).
- Single file/test: `npx vitest run path/to/thing.test.js` (or `-t "test name"` to filter by name); `npx playwright test e2e/viewer.spec.js` for one e2e spec.
- `npm run test:e2e` — builds the client then runs Playwright against the real built app (`e2e/*.spec.js`). First time: `npx playwright install chromium`.

`server/app.js` exports the Express `app` with no `.listen()` call specifically so tests can drive it in-process (via `supertest`) without a real port or the cron scheduler starting; `server/index.js` is the thin runtime entrypoint that adds those two things. One real Firestore emulator is started for the whole `vitest run` via a Vitest `globalSetup` (`server/__tests__/firestoreEmulatorGlobalSetup.js`, spawning `firebase-tools`'s `emulators:start` and writing its host/project info to a tmp-dir state file once ready). Per-test isolation is achieved differently than the old `mongodb-memory-server` approach (a fresh database per test): since `firebase-admin`'s app registry is a process-wide singleton (unlike a disposable `MongoClient`), each test instead gets a randomized `ACTIVE_SCHOOL` (e.g. `test-<uuid>`), and every read/write is already partitioned by `school`/`class`/`period` anyway. Integration tests (`server/__tests__/*.integration.test.js`) apply this via the shared `createTestApp()` helper in `server/__tests__/testApp.js`, which reads the emulator's connection info via `server/__tests__/firestoreTestEnv.js`'s `applyEmulatorEnv()` (the equivalent unit-test setup is inlined at the top of `timelineStore.test.js`/`historyStore.test.js` since those don't go through `app.js`) — **critically, this clears every already-`require`d `server/` module from Node's own `require.cache` by hand**, not via `vi.resetModules()` (which does not reliably bust CJS `require()` caching here); if you add a new server module that reads from `config.js` at require-time, this is why a stale value won't leak into the next test. Never reuse `createTestApp()`'s pattern with a bare `vi.resetModules()` only — it silently doesn't isolate. `createTestApp()` also blanks out the `CLOUDINARY_*` env vars before requiring `app.js`, since `dotenv` never overwrites an already-set var — without that, a real local `.env`'s Cloudinary credentials would leak into the test run and `imageStore.js` would make real network calls against your actual account instead of falling back to a data URI. `server/services/persistence/__tests__/contract.test.js` separately exercises the full persistence contract directly against `firestoreAdapter.js` - this is what a future second adapter would be checked against to confirm it's a drop-in replacement. `firestoreTestEnv.js` also exports `waitFor(fn)`, a small poll helper: a `.where()` query (unlike a point read by id) can briefly lag behind a just-written doc when the whole suite's ~20 parallel workers are all hammering the one shared emulator at once - a test that lists/queries right after writing should poll through this instead of asserting once (see its usages in the backup tests for the pattern).

Playwright's config (`playwright.config.js`) points `DATA_DIR` at an isolated temp dir too, and seeds it from the real `server/data/themes.json`: a genuine deployment always starts from the committed seed file (there's no API to *create* a new theme, only to switch the active one), so an e2e run against a truly empty `DATA_DIR` would test a state that can't actually occur. Keep that seeding if you add more e2e specs. Events don't live in `DATA_DIR` anymore, so its `webServer.command` points at `e2e/start-server.js` instead of `server/index.js` directly - that script boots its own separate Firestore emulator (own port/project, via `e2e/firebase.json`, so it can run alongside `npm test`'s emulator), seeds it from `server/data/timeline.json` (same "mirror a real deployment's starting state" rationale, just via Firestore now), then requires the real `server/index.js` in-process. `CLOUDINARY_*` is deliberately left unset for e2e too (explicitly blanked in `webServer.env`, in case the shell running it has real credentials exported) so the image-upload spec (`e2e/lightbox.spec.js`) exercises `imageStore.js`'s data-URI fallback rather than needing real Cloudinary credentials in CI.

### Linting

`npm run lint` runs ESLint (`eslint.config.js`, flat config). Three deliberate scope decisions, don't "fix" these without reconsidering why:
- `react/prop-types` is off — this is plain JS (no TypeScript), nothing anywhere uses PropTypes, so enforcing it would mean retrofitting every component rather than being a lint-config change.
- Only `react-hooks/rules-of-hooks` and `react-hooks/exhaustive-deps` are enabled from `eslint-plugin-react-hooks` — its `recommended` config (v7+) bundles React *Compiler* readiness rules (`purity`, `immutability`, `gating`, `static-components`, ...); this app doesn't use the Compiler, so those don't apply.
- `eslint` is pinned to `^9` — `eslint-plugin-react`'s peer range doesn't yet cover ESLint 10.

A **Claude Code hook** (`.claude/settings.json`, `PreToolUse`/`Bash`, filtered via `"if": "Bash(git push *)"`) runs `.claude/hooks/lint-before-push.js` before any `git push`-shaped Bash command and blocks it (via `permissionDecision: "deny"`) if `npm run lint` fails. `.claude/settings.json` and `.claude/hooks/` are deliberately carved out of the `.claude/*` gitignore rule (see `.gitignore`) so this hook is shared with anyone who clones the repo, not just a local preference.

### CI

`.github/workflows/ci.yml` runs on every `push` and `pull_request`: two parallel jobs, `test` (`npm test`) and `e2e` (installs Playwright's Chromium + OS deps, then `npm run test:e2e`). The e2e job uploads the Playwright HTML report as a build artifact if it fails (`playwright.config.js` only generates that report when `CI` is set — locally it's just the plain `list` reporter).

`.github/workflows/main-report.yml` is a separate, narrower workflow: it only triggers on a `push` to `main` (i.e. after a PR merges), and — unlike `ci.yml`'s e2e job, which only uploads its report on failure — it **always** runs both suites to completion and publishes a report regardless of outcome: a pass/fail table plus the tail of each suite's output written to the run's job summary (`$GITHUB_STEP_SUMMARY`), and the full logs + Playwright HTML report uploaded as a single `main-test-report-<sha>` artifact. It uses `if: always()` on the e2e/summary/upload steps specifically so a failing unit-test step doesn't skip the rest of the job and leave `main` without a report. There's no real GitHub webhook involved — a webhook only POSTs an event payload to an external endpoint and can't run anything itself, so "run tests and report after main updates" is implemented as this push-triggered Action instead.

### Versioning

`package.json`'s (and `client/package.json`'s, kept in lockstep) `version` field is bumped automatically by `.github/workflows/version-bump.yml` on every `push` to `main`: it reads the triggering commit's message and applies **conventional-commit-style detection** (`scripts/bump-version.js`'s `detectBumpType`) — `BREAKING CHANGE` anywhere in the message, or a `major:`/`feat!:` subject, is a **major** bump; a `feat:` subject is a **minor** bump; anything else (`fix:`, `chore:`, `docs:`, or no prefix at all) is a **patch** bump. It then commits the bump as `github-actions[bot]` with the message `chore: bump version to X.Y.Z [skip ci]`, tags it `vX.Y.Z`, and pushes both straight to `main`. The `[skip ci]` is load-bearing: combined with GitHub's native behavior of not re-triggering push-workflows for commits made with the default `GITHUB_TOKEN`, it's a second, explicit guard against the workflow looping on its own bump commits — there's also a same-workflow guard step that checks the latest commit message before doing anything. This requires `permissions: contents: write` in the workflow and assumes `main` has no branch protection blocking direct pushes from Actions; if that's ever turned on, this workflow needs an exemption or a different token.

`scripts/bump-version.js` is also exposed for deliberate manual releases via `npm run release:major` / `release:minor` / `release:patch` — these skip the commit-message detection and just apply the given bump type directly to both `package.json` files (uncommitted; you review and commit yourself). Don't run one of these *and* rely on the next merge's auto-bump for the same change — they're not coordinated, so you'd double-bump.

The client embeds the root `package.json` version at build time as the `__APP_VERSION__` global — set via `define` in both `client/vite.config.js` and the root `vitest.config.js` (so component tests see the same global without a real build), and declared for ESLint in `eslint.config.js`'s client globals block. `client/src/version.js` re-exports it as `APP_VERSION`; `Footer.jsx` (viewer) and `AdminPage.jsx` display it. There's no server-side `/api/version` — the version is a client build-time constant, not something fetched at runtime.

## Architecture

### Data model

Events live in Firestore now (not a JSON file), behind a pluggable persistence layer — see **Persistence: a pluggable layer, Firestore + Cloudinary** below for why, the layer's design, and the full document shapes. Every API response and the in-memory item shape everywhere else in the codebase (client, `eventsApi.js`, tests) is still exactly:
```
{ id, type: "holiday"|"test"|"notice"|"project", m: 1-12, y, title, short, full,
  detail: { pages?, words?[], links?[{label,url,ph?}], images?[{id,url}] }, "required-white-shirt"?: boolean }
```
`server/services/timelineStore.js` strips persistence-only fields (`school`, `class`, `period`, `status`, timestamps) before returning anything, so nothing outside that module needs to know how/where data is stored.

`required-white-shirt` and `required-food` (both optional, default `false`) mark an item that needs a white shirt (e.g. sports day) or that parents should send food for (e.g. a class party). The viewer renders a pulsing badge next to such items — `client/src/viewer/WhiteShirtIcon.jsx` / `FoodIcon.jsx`, sharing the `.reminder-badge` pulse styling in `timeline.css` — to draw attention; an item can carry both flags at once. Adding another such reminder flag later means: a new optional boolean in `validateItemInput`/`addItem` (`timelineStore.js`), a new icon component reusing `.reminder-badge`, a render check in `ItemRow.jsx`/`ItemDetail.jsx`, and a checkbox in `ItemForm.jsx`.
Hebrew month names are derived from a month-number lookup (`server/services/hebrewMonths.js`, mirrored in `client/src/hebrewMonths.js`) rather than stored per item. The viewer (`client/src/viewer/ViewerPage.jsx`) groups items by `(y, m)` and sorts chronologically to rebuild the month blocks.

`detail.images` holds `{id, url, publicId}` entries. `url` is a Cloudinary-hosted `https://` URL (or an inline `data:` URI if Cloudinary isn't configured — see below); either way it's just a string the client drops straight into `<img src>`, so nothing client-side cares which. Images are uploaded/removed via dedicated admin-only sub-routes (`POST`/`DELETE /api/timeline/items/:id/images[/:imageId]` in `timeline.routes.js`, multipart via `multer` into memory, never disk) which go through the normal `timelineStore.updateItem` path underneath, so image changes are validated and show up in history like any other edit. Deleting an image reference never calls out to delete the backing Cloudinary asset (so old history snapshots referencing it still resolve) — a deliberate, unbounded tradeoff like the history retention gap below. The admin upload UI (`client/src/admin/ImageManager.jsx`, used from `ItemForm.jsx` — edit-only, since uploading needs an existing item id) posts directly to those routes. In the viewer, clicking a thumbnail (`ItemDetail.jsx`) opens it in `client/src/viewer/Lightbox.jsx` (a full-page in-app overlay with zoom buttons + mouse wheel, Escape/backdrop/× to close — never a plain `<a href>`, so it never triggers a browser download) via the `LightboxProvider` context (`client/src/viewer/LightboxProvider.jsx`, wrapped around the app in `App.jsx` next to `ThemeProvider`) so any component can call `useLightbox().open(url)` without prop-drilling.

`server/services/timelineStore.js` owns all reads/writes: input validation (`validateItemInput`, unchanged — pure and synchronous, no DB access) plus orchestrating calls into the persistence layer (`getRepository()`, see below). Never query Firestore (or any future backend) directly from a route handler, or from `timelineStore.js`/`historyStore.js` themselves — go through `server/services/persistence/`.

Themes are unaffected by this: still a separate file, `server/data/themes.json`: `{ activeThemeId, themes: [{id, name, vars: {--bg, --paper, ...}}] }`, seeded from the two CSS variable sets in `timeline.html`'s `:root` blocks. `client/src/theme/ThemeProvider.jsx` fetches this and applies `vars` onto `document.documentElement.style` at runtime — **adding a new theme is a data change only** (POST/seed a new entry in `themes.json`), no CSS edits needed. The base CSS (`client/src/styles/timeline.css`) still carries the original light/dark values as a fallback so nothing is unstyled before JS runs.

### Persistence: a pluggable layer, Firestore + Cloudinary

The original design kept everything in `server/data/*.json`/`*.jsonl` on local disk. That broke on any real deploy: a hosting platform's filesystem is typically ephemeral or gets reset to the git checkout on redeploy, silently discarding any edits made through `/admin` since the last commit. A second attempt moved events into MongoDB Atlas - but the free M0 tier turned out to be a shared, throttled tier that Vercel's serverless functions (each opening a fresh TLS connection per cold start) overloaded, producing intermittent `MongoServerSelectionError`/TLS-alert failures in production. Events (and their history) now live in **Firestore** (free Spark plan - reached over plain HTTPS, so there's no persistent driver connection to throttle) instead, and event images still live in Cloudinary. `themeStore.js` was deliberately left on the old file-based approach — out of scope for both changes, since theme-switching isn't user-facing data that gets lost the same way.

**The DB itself is swappable without touching anything above it.** `server/services/persistence/` is the only place in the codebase allowed to know what Firestore is:
- `contract.js` — no runtime logic, just the documented method list (and required shapes) every adapter must implement: `getActiveEvents`, `getEvent`, `createEvent`, `updateActiveEvent`, `restoreEvent`, `listHistory`, `getHistoryEntry`. Every method takes a `tag` (`{school, class, period}`).
- `firestoreAdapter.js` — the Firestore implementation of that contract: the lazily-initialized `firebase-admin` client singleton (reused across warm Vercel invocations the same way the old Mongo client was), collection refs, and `runTransaction()`-backed atomic writes.
- `index.js` — `getRepository()`, returning the adapter picked by the `DB_PROVIDER` env var (defaults to `"firestore"`). Adding a second backend later means writing one new adapter file and switching this value - not touching `timelineStore.js`, the routes, or the client.

`timelineStore.js`/`historyStore.js` call only `getRepository()`'s contract methods — never `firebase-admin` directly - and own all the business logic (validation, deciding what a "create" vs "update" vs "restore" means, computing `before`/`after` snapshots), passed into the adapter as a synchronous `computeChange` callback so the adapter can apply it atomically alongside its own read.

Firestore holds two collections:
```
events:  { school, class, period, status: "active"|"deleted",
           type, m, y, title, short, full, detail, "required-white-shirt", "required-food",
           createdAt, updatedAt }   // doc id = the event's own id

history: { school, class, period,  // denormalized, so the global feed can filter without a join
           itemId, ts, op, title, before, after }   // doc id = the entry's own id
```
Unlike the old Mongo document, `history` is now its own top-level collection rather than an array embedded in its event - Firestore has no efficient way to query "which document has an array element whose sub-field X equals Y" (needed by restore, which looks up the owning event from a history entry id), so a flat collection keyed by the entry's own id turns that into an O(1) lookup instead of a scan. No composite Firestore index is needed anywhere: every query is pure-equality `where()` with no `orderBy`, and `historyStore.list()`'s newest-first sort + `limit` happen in application code after fetching rather than via Firestore's native `orderBy` (which would force one) - sound at this app's scale (one school year, low hundreds of docs).

`school`/`class`/`period` (e.g. `reut`/`e4`/`2026-2027`) tag which dataset an event or history entry belongs to, so several schools/classes/years can share one Firestore project without colliding. `ACTIVE_SCHOOL`/`ACTIVE_CLASS`/`ACTIVE_PERIOD` (env vars, see Commands above) pick which dataset a given server instance reads/writes; switching datasets today means changing those and redeploying — there's no runtime admin UI for it yet (deliberately deferred; the schema is ready for one). `scripts/migrate-to-firestore.js` is a one-off, safely-rerunnable script that loads `server/data/timeline.json` into Firestore under the active dataset tag; it's how the original demo data got seeded, not something the running app calls. `scripts/export-from-atlas.js`/`scripts/import-to-firestore.js` are the one-time cutover pair used to move a live production dataset off the old Mongo Atlas cluster (export is read-only against Atlas; import is idempotent, upserting by id so history entries keep their original, individually-restorable ids) - temporary tooling, not part of normal operation.

Deletes are soft (`status: "deleted"`, document never removed) rather than hard, specifically so a deleted item's history stays reachable for the undelete flow described below — `getAll`/`getItem` simply filter to `status: "active"`.

Event images go through `server/services/imageStore.js`, a thin Cloudinary wrapper (`CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET`). If those aren't set — a fresh clone before `.env` is configured, or CI/e2e deliberately running without them — `uploadImage` falls back to returning the upload as an inline `data:` URI instead of failing outright; this is a dev/test convenience, not meant for production use (every image bloats its owning Firestore document instead of living on a CDN).

### History & recovery

### API (`server/routes/`)

- `GET /api/timeline` — public, full item list.
- `POST /api/timeline/items`, `PUT /api/timeline/items/:id`, `DELETE /api/timeline/items/:id` — admin-only (`requireAuth` middleware).
- `POST /api/timeline/items/:id/images` (multipart, field `image`), `DELETE /api/timeline/items/:id/images/:imageId` — admin-only; see **Data model** above for the images mechanism.
- `POST /api/timeline/import` (multipart, field `file`, a `.json` file) — admin-only; bulk-loads items in the same shape `GET /api/timeline` returns (`{ items: [...] }`, or a bare array). This is the backing endpoint for the "ייבוא נתונים" panel on `/admin` (`client/src/admin/ImportPanel.jsx`). Semantics, deliberately chosen over simpler alternatives: **merge by id** (an item whose `id` matches an existing one overwrites it like `updateItem`; everything else is created like `addItem`, with a fresh id) and **all-or-nothing validation** (`timelineStore.importItems` runs `validateItemInput` over every item first and aborts the whole import — writing nothing — if any one of them fails, returning `{ error, details: [{index, error}] }`). Validation still runs as one upfront, all-or-nothing pass before any write happens, but once writing starts each item is its own Firestore document write (atomic per-document via a transaction, not one all-or-nothing transaction across the whole batch — a known, accepted tradeoff at this app's scale); history still gets one `create`/`update` entry per item, so each imported item remains individually revertable via the normal history/restore flow.
- `GET /api/themes` — public. `PUT /api/themes/active` — admin-only.
- `POST /api/auth/login` (checks `ADMIN_PASSWORD`, sets `express-session` cookie), `POST /api/auth/logout`, `GET /api/auth/me`.
- `GET /api/history?itemId=&limit=`, `POST /api/history/:eventId/restore` — admin-only, see **History & recovery** below.
- `GET /api/events` — public, stable contract for external consumers (e.g. a future calendar export). Deliberately separate from `/api/timeline`: `server/services/eventsApi.js` maps internal items to a decoupled shape (`month`/`year` instead of `m`/`y`, `shortDate`/`fullDate` instead of `short`/`full`, `requiresWhiteShirt`/`requiresFood` instead of the hyphenated internal keys, placeholder links resolved to `url: null`) so external callers aren't coupled to internal field-naming changes. If you add a new internal item field, decide deliberately whether it belongs in this mapping too — don't assume it should just pass through.
- `GET /api/backup`, `POST /api/backup`, `POST /api/backup/:id/restore` — admin-only, see **Backups** below. `GET /api/backup/run` is separately gated by `requireCronSecret` (not `requireAuth`) instead, since it's hit by an automated caller, not a logged-in admin.

### History & recovery

Every mutation in `server/services/timelineStore.js` (`addItem`/`updateItem`/`deleteItem`/`restoreFromHistory`) writes a new entry into the `history` collection atomically alongside the event doc's field changes, via the persistence layer's `runTransaction()`-backed `updateActiveEvent`/`restoreEvent` methods (see **Persistence** above): `{ id, ts, op: "create"|"update"|"delete"|"restore", itemId, title, before, after }`. `server/services/historyStore.js` is read-only — it just asks `getRepository()` for entries rather than storing anything itself; the one place history entries get written is `timelineStore.js`, since a legitimate entry is always tied to a real event document. `timelineStore.restoreFromHistory(eventId)` is the one restore path for both use cases — undeleting (restores a `delete` entry's `before` snapshot, and flips `status` back to `"active"`) and reverting properties (restores any other entry's `after` snapshot) — and itself logs a new `restore` entry, so a restore can later be undone the same way. The admin UI (`client/src/admin/HistoryPanel.jsx`) shows a global feed (needed since a deleted item no longer appears in the normal item list — soft-delete keeps its document, and therefore its history, around) or a per-item feed via the "היסטוריה" button in `ItemList.jsx`. The history log has no retention/pruning yet — a natural future job for the scheduler hook below.

### Backups

Full-dataset backups, on top of the same persistence layer as events/history (`server/services/backupStore.js`, plus `createBackup`/`listBackups`/`getBackup` added to the persistence contract and `firestoreAdapter.js`). A `backups` Firestore collection holds one document per calendar date (`school`/`class`/`period` tagged like everything else), each a full snapshot: `{ createdAt, itemCount, items: [...], themes: { activeThemeId } }` — `items` is the exact shape `GET /api/timeline` returns, and the doc id (e.g. `"2026-10-23"`) is itself the "indexed by date" lookup key; a second backup taken the same day overwrites the first.

**Scheduling, and why there are two trigger paths.** The intended cadence is "every two weeks," but cron syntax has no native "every N weeks" expression, and there's a second wrinkle specific to this app's two deployment modes: `server/jobs/scheduler.js`'s `node-cron` jobs only ever start from `server/index.js`'s `scheduler.start()` call (the `npm start` / always-on process) — **not** from the headless `server/app.js` that Vercel's `api/index.js` requires for the serverless deployment (see the Commands section above), so node-cron never runs in production on Vercel at all. Both problems are solved the same way: a cron tick (`BACKUP_CRON`, default every Sunday) only *checks* whether a backup is due; `backupStore.runScheduledBackupIfDue()` is what actually enforces the real cadence, by comparing against the last backup's own `createdAt` against `BACKUP_MIN_INTERVAL_DAYS` (default 14) rather than counting ticks — which also means a missed tick (server was down, a deploy was mid-flight) just backs up on the next one instead of permanently skipping a cycle. `server/jobs/backupJob.js` calls that function directly for the node-cron path; `GET /api/backup/run` (gated by `requireCronSecret`, `server/middleware/cronAuth.js`) calls the exact same function for Vercel, which `vercel.json`'s `crons` entry hits on the same weekly schedule — Vercel Cron Jobs only issue GET requests, which is why that route is a GET despite triggering a write. Vercel automatically attaches `Authorization: Bearer <CRON_SECRET>` to its own requests to a cron-configured path once `CRON_SECRET` is set as a project env var; that's the only thing gating that route otherwise, so it must be set in production.

**Restore is deliberately best-effort, never all-or-nothing** — unlike `importItems` (which validates every item up front and writes nothing at all if any one fails). `timelineStore.restoreAllFromBackup(items)` replaces the *entire* active dataset with a backup's snapshot: every item in the backup is recreated (or overwrites a same-id doc, active or soft-deleted, via `createEvent`'s upsert-by-id), and every currently-active item *not* in the backup is soft-deleted (same as a normal `deleteItem`, so it's still individually undoable from history afterward). Each backup item goes through `sanitizeBackupItem` first, which independently defaults every bad/missing field (`type`→`"notice"`, `m`→`1`, `y`→this year, `title`/`short`/`full`→`""`, non-array `detail.words`/`links`/`images`→`[]`) rather than rejecting the item — a field that had to be defaulted is named in that item's `recoveryIssues` array (a normal first-class item field now, alongside `required-white-shirt`; always `[]` unless it came from a restore that had to default something, and reset to `[]` the next time the item is saved normally through the admin UI). A write-level failure (as opposed to a data-shape one) skips just that one item into the result's `skipped` list instead of failing the whole restore. The admin UI (`client/src/admin/ItemList.jsx`) shows a "שוחזר חלקית" badge on any item with a non-empty `recoveryIssues`, with the specific field names in its tooltip.

The admin UI for all of this is `client/src/admin/BackupPanel.jsx` (list backups, "גיבוי עכשיו" to back up on demand, restore any backup) on `/admin`.

### Client (`client/src/`)

- `viewer/` — mirrors the original static page's DOM structure and class names exactly (`.masthead`, `.rail-cell`, `.date-tag`, `<details class="item">`, etc.) against the ported `styles/timeline.css`, so visual output matches `timeline.html`. `ViewerPage.jsx` fetches `/api/timeline` on mount; current-month detection and the "jump to current month" scroll button are ported as-is from the original inline script.
- `admin/` — `AdminPage.jsx` gates on `GET /api/auth/me`; shows `LoginForm` until authenticated, otherwise item add/edit/delete (`ItemForm`, `ItemList`, with `ImageManager` nested for editing an existing item's images), `ThemeSwitcher`, `HistoryPanel`, `ImportPanel`, and `BackupPanel` (see **Backups** above).
- `App.jsx` routes `/` (viewer) and `/admin` via `react-router-dom`.

### Scheduler hook (`server/jobs/`)

`scheduler.js` registers cron jobs (via `node-cron`) at server boot, driven by `SCHEDULER_CRON`. `exampleJob.js` is a **no-op placeholder** — this is the intended extension point for a future recurring "business flow" that changes the timeline data periodically (e.g. auto-archiving past items, pulling from an external source). No real logic is implemented yet; add new jobs by exporting a `run()` function and registering it in the `JOBS` array in `scheduler.js`. `backupJob.js` is the one real job registered here so far (see **Backups** above) — and, notably, only actually runs in the `npm start` deployment mode; the Vercel/serverless deployment relies on `vercel.json`'s `crons` hitting an HTTP endpoint instead, since node-cron never starts there at all.

## Editing the data

Use the `/admin` page (password from `ADMIN_PASSWORD`), not the database directly — it goes through `timelineStore`'s validation. `server/data/timeline.json` itself is no longer read by the running app; it's kept only as the seed fixture for `scripts/migrate-to-firestore.js` and for e2e (`e2e/start-server.js`). The two Hebrew `.txt` files at the repo root (`דרישות מעניינות.txt` — feature ideas; `לח מבחנים-מחצית ראשונה.txt` — first-semester exam dates) were the source for that original seed data and are no longer the live source of truth.
